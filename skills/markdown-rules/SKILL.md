# Markdown 작성 규칙

사용자가 이 스킬을 명시적으로 지정한 작업에서만 다음 규칙을 적용한다. 사용자가 지정한 언어·형식·경로와 작업 공간의 문서 규약을 우선한다. 포맷을 맞추기 위해 요청 범위를 넓히거나 관련 없는 문서를 수정하지 않는다.

## 문서 구성

- 목적, 적용 범위, 핵심 조건을 먼저 제시한다. 판단에 필요하지 않은 배경 설명과 제목을 반복하는 도입문은 생략한다.
- 설명·참조 문서는 사실과 근거를, 작업 지침은 조건과 행동을 중심으로 구성한다. 모든 설명을 명령문으로 바꾸지 않는다.
- 구체적인 제목을 사용한다. `기타 사항`보다 `CSV 날짜 검증 규칙`처럼 대상과 내용을 드러낸다.
- 한 절은 하나의 주제, 한 규칙은 하나의 판단이나 행동을 다룬다. 짧은 문서에는 불필요한 절·목차·요약을 추가하지 않는다.
- 작업 지침에는 필요한 입력, 기대 결과, 완료 기준을 명시한다. 누락된 정보와 실패 상황의 처리 방식은 실제 작업에 필요한 만큼만 기술한다.

## 문장과 의미

- 간결하고 직접적인 문장을 쓴다.
- 같은 개념에는 같은 용어를 사용한다. 검색에 필요한 별칭이나 약어는 처음 등장할 때 연결한다.

## Markdown 포맷

- 기본 Markdown 문법을 우선한다. 표 등 확장 문법은 대상 환경의 지원 여부를 고려한다.
- 제목은 `#`, `##`, `###`로 계층을 표현하며 중간 단계를 건너뛰지 않는다. 독립 문서의 제목은 보통 H1 하나로 두되, 제목을 별도로 관리하는 형식과 기존 템플릿을 따른다.
- 제목, 문단, 목록, 표, 코드 블록의 경계에는 빈 줄을 둔다. 구조를 전달하는 줄바꿈과 들여쓰기를 토큰 절감 목적으로 제거하지 않는다.
- 순서가 의미 있는 절차는 번호 목록, 독립 항목은 글머리표로 작성한다. 중첩은 실제 포함 관계에만 사용하고, 긴 분기는 별도 절로 나눈다.
- 같은 속성을 비교할 때 표를 사용한다. 셀에 긴 설명이나 복잡한 조건이 필요하면 목록이나 절로 바꾼다. 표 정렬을 위한 과도한 공백은 넣지 않는다.
- 식별자·짧은 명령어·리터럴은 인라인 코드로, 여러 줄의 코드·명령·데이터는 언어 또는 형식을 명시한 코드 블록으로 작성한다. 실행 가능한 예시에는 불필요한 출력이나 설명을 섞지 않는다.
- 링크는 대상 내용을 설명하는 이름으로 작성한다. 추가 자료를 언제 읽을지 명확하지 않으면 읽는 조건을 함께 쓴다. 배포하는 문서 묶음에서는 기준 위치가 분명한 상대 경로를 사용한다.
- 굵게 표시는 핵심 용어나 제약에 제한한다. 색상·아이콘·이미지에만 의존해 필수 조건을 전달하지 않는다. 판단에 필요한 정보는 텍스트로도 제공한다.
- 장식용 구분선, 반복 강조, 불필요한 HTML은 생략한다. YAML frontmatter는 스킬 규격이나 실제 소비 도구가 요구할 때 사용한다.

## 읽기 범위와 토큰 사용

- 독자가 이미 아는 일반 설명, 중복 규칙, 같은 판단을 반복하는 예시를 줄인다. 도메인 고유 조건과 중요한 경계 사례는 남긴다.
- 항상 필요한 내용은 진입 문서에 둔다. 특정 작업에서만 필요한 상세가 충분히 크면 참조 파일로 분리하고, 진입 문서에 내용·경로·읽는 조건을 안내한다.
- 작은 문서를 무조건 나누지 않는다. 파일을 나눠도 전부 읽게 하면 절감되지 않으며, 지나친 분리는 추가 탐색을 유발한다.
- 함께 필요한 조건·행동·예외는 가까이 둔다. 참조는 가능한 한 진입 문서에서 직접 연결하고, 긴 참조 사슬을 피한다.
- 한 절만 읽어도 대상과 적용 조건을 파악할 수 있게 한다. 이를 위한 최소한의 맥락은 유지하되 규칙 전체를 복제하지 않는다.
- 규칙의 원문은 한 곳에서 관리한다. 다른 위치에는 필요한 요약과 원문 위치를 제공하며, 요약과 원문이 충돌하지 않게 한다.
- 길고 탐색이 필요한 문서에는 짧은 목차나 탐색 안내를 둔다. 짧은 문서에는 자동으로 추가하지 않는다.
- 토큰 절감을 이유로 영어 변환, 임의 약어, 공백 제거, 표·JSON·YAML·XML 변환을 일괄 적용하지 않는다. 문서 역할과 소비 방식에 맞춰 선택한다.
- 고정된 줄 수·문자 수·토큰 수를 모든 문서의 최적 길이로 취급하지 않는다. 토큰 수 비교가 요청되면 대상 모델에 맞는 측정 방법을 사용하고, 측정하지 않은 절감률은 주장하지 않는다.
- 일반적인 문서 작성에는 별도의 토큰 측정이나 성능 실험을 추가하지 않는다. 최적화 평가가 작업 범위에 포함되면 문서 토큰뿐 아니라 실제 읽기량, 추가 탐색·재시도, 완료 정확도를 함께 확인한다. 캐싱에 따른 비용 절감은 문서 길이 감소와 구분한다.

## 작성 후 점검

- 원래 의도, 필수 조건, 예외, 수치, 부정 표현을 보존했는지 확인한다.
- 제목과 용어만으로 필요한 규칙을 찾을 수 있고, 일부만 읽어도 적용 조건이 명확한지 확인한다.
- 제목 계층, 목록 들여쓰기, 표, 코드 펜스, 링크 경로가 올바른지 확인한다. 기존 문서나 외부 자료의 경로는 가능한 범위에서 실제로 확인한다.
- 중복·모순·불필요한 배경을 제거하고, 예시와 본문 규칙의 일치를 확인한다. 결과 보고에는 요청된 산출물과 실제 수행한 검증만 간결하게 전달한다.
